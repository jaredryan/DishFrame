# DishFrame Code Audit — 2026-08-27

Comprehensive engineering audit and cleanup pass across the entire repository (App Router, components, `src/lib` business logic, Prisma schema/migrations, scripts, CI, and tests). Conducted via six parallel read-only investigations (Recipe/Part core, Cooking Mode, Meal Plans/Grocery Lists, Sharing/Export, shared infra & auth, tooling/tests/CI/deps), followed by direct implementation of the safe findings — and, in a same-day follow-up pass, resolution of the three findings that originally needed an owner decision.

## Executive summary

DishFrame's engineering quality is unusually high for a project this size. Every domain reviewed shares the same disciplined patterns: ownership-scoped queries (never fetch-then-check), doc comments that cite the exact spec section and explain _why_ a decision was made (not just what the code does), and consistent two-layer authorization (session + ownerId). No dead code, no unsafe casts, no SQL injection risk, and no authorization gaps were found anywhere in the six domains audited.

The findings that did surface fall into three recurring themes:

1. **A handful of near-identical bugs/gaps that were already caught once but not propagated.** The clearest example: `reorderTasters`'s "must equal the complete owned set" validation was correctly fixed at some point, but the same bug pattern survived in `reorderGroceryCategories`. `PartUsageResolutionKind`/`PartUsageResolutionValue` were the same union declared twice. This is the normal residue of iterative feature development, not a systemic quality problem.
2. **N+1 query patterns in "fold an added item into an existing combinable item, else create one" loops**, in `grocery/list-service.ts`. Three call sites each re-queried every `GroceryListItem` (plus a separate max-position aggregate) once per added ingredient, instead of once per operation.
3. **A few small, genuinely duplicated UI/DTO-mapping blocks** across page/layout pairs that are easy, low-risk wins to extract.

All three items that originally needed an owner decision (MATERIALIZED PartLink fidelity, the grocery sync-flag gap, and publication state in export) were given final product direction and implemented the same day — see "2026-08-27 follow-up" below. One further discovery surfaced while implementing that follow-up — the account/Dish JSON export format has no restore/import path anywhere in the codebase — and has since been resolved as a decision, not left open: it's a deliberately deferred standalone feature, tracked at the top of `docs/TODO.md`'s Tier 3 section (see item 3 below).

## 2026-08-27 follow-up: owner-decision items resolved

The three findings originally listed under "Needs owner decision" were given final product direction the same day and implemented. They're recorded here rather than erased, since the original findings and reasoning are still useful context for anyone reviewing the history.

### 1. MATERIALIZED PartLink content preserved across all reproduce/promote/materialize paths

**Decision:** any operation whose purpose is to reproduce, promote, duplicate, or further materialize a Version must preserve a MATERIALIZED PartLink snapshot it already contains, matching the fidelity the sharing copy engine (`createIndependentCopyFromGraph`) already had.

**Implementation** (`src/lib/dishes/queries.ts`, `src/lib/dishes/service.ts`): added `partLinkContentIncludeAllStates` (both `linkState`s, plus the materialized-only columns) and `getDishScopedVersionContentForReuseOrThrow` alongside the existing LIVE-only `partLinkContentInclude`/`getDishScopedVersionContentOrThrow` — the LIVE-only pair stays exactly as it was for callers that only ever show/diff _editable_ content (the editor, comparison views), which correctly never show a MATERIALIZED occurrence in the first place.

Added a shared reproduce-path mapper in `service.ts`: `toInsertablePartLinkInput`/`versionContentToInsertableInput` convert an all-states row into `InsertablePartLink`/`InsertableSection` — a LIVE row exactly like the existing `toPartLinkInput`, a MATERIALIZED row carried through **verbatim** (its `materializedContent` is already frozen, self-contained JSON from whenever it was originally materialized; reproducing it faithfully means copying it unchanged, never re-walking or remapping it — unlike the sharing engine's `remapRef`, which _does_ rewrite nested LIVE targets because a share copy crosses accounts).

Fixed, using this shared mapper:

- `duplicateDish` and `promoteHistoricalVersion` — straightforward swap to the all-states include/mapper; both already just hand the result to `insertSections` (which already accepted the wider `InsertablePartLink`/`InsertableSection` types).
- `resolveMaterializedSnapshot` — same swap; this is the one that also fixes the two-level "Part-in-Part" chain, since the Part being deleted can itself already hold a MATERIALIZED occurrence.
- **Two more call sites with the identical bug, found while implementing the shared fix and corrected as part of the same general principle** (not separately requested, but the same "reproduce this Version's content" pattern): `propagateToOneContainer` and `resolvePartUsageOccurrence` both reconstruct a container's entire Version to change one specific LIVE occurrence, and were silently dropping any _unrelated_ MATERIALIZED occurrence elsewhere in that same Version. Since their existing dup-check/cycle-check/occurrence-matching logic is genuinely LIVE-only (a MATERIALIZED entry has no live target to check), added `splitLiveAndMaterialized`/`mergeMaterializedBack` — a "sandwich" that runs all of that existing logic against a LIVE-only view unchanged, then merges the untouched MATERIALIZED occurrences back in immediately before `insertSections`. Also added `removeEmptySectionsPreservingMaterialized`, since the existing (LIVE-only) `removeEmptySections` would otherwise drop a Section whose only remaining content is a MATERIALIZED occurrence.

**Deliberately not touched:** `editDish`. Its content comes wholesale from the editor's submitted `input`, which never shows a MATERIALIZED occurrence in the first place (it's frozen history, not editable) — so "preserve it through an edit the user can't see or control" is a different, unresolved product question (does an ordinary content edit intentionally drop historical materialized debris, or should it silently carry it forward forever with no way to remove it via the UI?), not a straightforward extension of this fix. Flagged, not decided.

**Tests:** `src/lib/dishes/dishes.integration.test.ts` — a new `describe("Code-audit fidelity fix — MATERIALIZED PartLink preservation")` block with three tests, built via the same real `deletePart` Phase 2 materialization path the existing "deletePart (Phase 2)" suite uses (not a fabricated row): `duplicateDish` preserves a MATERIALIZED link; `promoteHistoricalVersion` preserves one; and a nested/second-level chain (Part B materializes Part A, gets promoted so Part B's _current_ content legitimately holds a MATERIALIZED occurrence, then Part B itself gets deleted) proves `resolveMaterializedSnapshot` preserves the nested MATERIALIZED entry inside the newly-frozen snapshot.

### 2. Grocery sync-flag gap fixed generally, not special-cased

**Decision:** this is a bug — the sync flag must reflect the item's actual material state, and a substitute selection must never mask an unrelated quantity/removal change.

**Root cause:** `resyncGroceryListFromMealPlan`'s "Unchanged/changed" loop (`src/lib/grocery/list-service.ts`) decided whether a contribution had changed (`differsFromStoredLive`) by comparing only the **primary** snapshot fields (`originalName`/`quantityText`/`unit`/`isOptional`) against the fresh occurrence — never the **substitute** snapshot fields, even though a contribution with `selectedVariant: "SUBSTITUTE"` displays the substitute values. A change to the substitute's own quantity, or the substitute disappearing entirely (which also reverts `selectedVariant` back to `"PRIMARY"`), went completely undetected whenever the primary fields happened to stay the same.

**Fix:** `differsFromStoredLive` now also compares the freshly-computed substitute snapshot (`substituteName`/`substituteQuantityText`/`substituteUnit`, via the existing `substituteSnapshotFields` helper) against what's stored — a general correction to the diff, not a fixture-specific patch, and it fires regardless of which variant is currently selected/displayed (the underlying synced data changed either way).

**Tests:** `src/lib/mealplans/mealplans.integration.test.ts`, in the existing "grocery synchronization" suite — two new tests: a chosen substitute's own quantity changing on resync is now flagged `CHANGED`, and a chosen substitute disappearing entirely on resync (reverting to `PRIMARY`) is now flagged `CHANGED`. Both build the scenario through the real `selectGroceryItemVariant` → `editDish` → `adoptNewerVersionInEntry` path, matching the existing test in that suite that proves the _unrelated_-resync case correctly stays `UNCHANGED` (which the fix does not regress).

### 3. Active public-publication state added to account/Dish export

**Decision:** export/backup should represent an item's _active public ShareLink state_ (mode, fixed-version target, `showCreatorName`, `expiresAt`, `createdAt`) so it can be recreated — with a **freshly generated token/URL**, never the original secret — but must never include `DirectShare`/`DirectShareCollection` (sends to another account, acceptance history, recipient relationships) or any raw token/credential.

**Implementation** (`src/lib/importExport/export-dto.ts`): added `DishPublicationDto` plus `activePublicationsForDish`/`activePublicationsByDishId` (the latter batched — one query for all of an owner's active ShareLinks, grouped by dishId, instead of one query per exported Dish). Both `buildDishExportDto` and `buildAccountBackupDto` now include a `publications: DishPublicationDto[]` array per Dish — empty when there's no active publication, one entry per active `ShareLink` (a Dish can have more than one, e.g. a `CURRENT` link and a `FIXED_SNAPSHOT` of an older Version simultaneously). Revoked and expired links are excluded (matches the sharing service's own "active" definition). The `mode`/`showCreatorName`/`expiresAt`/`createdAt` fields, and the `FIXED_SNAPSHOT` target's version _label_ (not id — ids aren't portable), are included; `tokenId` and the frozen snapshot content are never queried into this DTO at all. The module's stale doc comment (which said sharing was excluded because "no sharing creation service exists yet" — false since Slices 16–22) is corrected. `CURRENT_EXPORT_FORMAT_VERSION` bumped 1 → 2 for the shape change.

**Genuinely new discovery while implementing this: there is no restore/import path for this export format anywhere in the codebase.** The "regenerate a fresh token on restore, using the real `createShareLink` service" half of the decision has nothing to attach to today — the only import feature in `importExport/` is the free-text paste-a-single-recipe importer, unrelated to this structured export/backup payload. Building a full restore feature was out of scope for this pass; the export-side improvement stands on its own regardless. **Resolved as a decision in a later pass** (not left open): a real restore feature is a deliberately deferred standalone Tier 3 feature, not a fidelity gap in this work — see `docs/TODO.md`'s Tier 3 section for its intended eventual semantics (non-destructive restore into fresh ids, relationship remapping, active public-publication state recreated with fresh tokens, direct-sharing relationships intentionally not portable).

**Tests:** `src/lib/importExport/import-export.integration.test.ts` — updated the two existing `formatVersion` assertions (1 → 2) and the account-backup test to assert an empty `publications: []` by default; added three new tests: an active `CURRENT`-mode publication appears in the account backup with the correct fields and no raw token anywhere in the serialized payload; an active `FIXED_SNAPSHOT` publication appears with the correct version label in both the Dish export and the account backup, while a separately revoked publication on the same Dish is excluded; and `DirectShare`/`DirectShareCollection` rows (sender/recipient email, `recipientLookup`) never appear in the account backup at all.

## 2026-08-27 third follow-up: orphan ImageAsset cleanup and metadata/crawler correctness

A separate, narrower pass (not a re-audit) closing two items that were living as accepted gaps/manual-checklist items in `docs/TODO.md` rather than as findings in this document.

### 1. Abandoned-upload ImageAsset cleanup implemented

**Gap:** `uploadAndNormalizeImage`'s own doc comment (`src/lib/images/service.ts`) had long documented that an `ImageAsset` created via upload-token issuance but never attached to a saved `DishVersion` (an abandoned edit) had no cleanup path — `deleteImageAssetIfOrphaned`'s reference-counted cleanup (the GIN-indexed query discussed in the second follow-up's item 5) only ever runs when a `DishVersion` *stops* referencing an asset, which never happens for one that was never attached in the first place.

**Implementation:** new `cleanupAbandonedImageAssets()` in `images/service.ts`, run by a new `/api/cron/cleanup-orphan-images` route on a daily Vercel Cron schedule (`vercel.json`), authorized via `CRON_SECRET` (Vercel's standard Bearer-header convention; added to the env schema and `.env.example`). Candidates are `ImageAsset` rows with no `DishVersion` at all, older than a 24h minimum age (conservative enough that no in-progress edit can race it), processed in bounded batches of 200 oldest-first per run.

Deliberately **Blob-first**, the opposite order from `deleteImageAssetIfOrphaned`: that function deletes the DB row first and best-effort-deletes the Blob object after, which is fine there since the row is the primary record of a larger operation (Dish/account deletion). Here the `ImageAsset` row is the *only* remaining record the Blob object exists at all — deleting it before the Blob delete succeeds would turn any Blob API failure into a silent, permanent, un-retryable storage leak. So each candidate's Blob object is deleted first; the row is only removed once that succeeds, and a Blob failure leaves the row in place for the next day's run.

**Follow-up correction (same day): a plain recheck-before-delete does not actually close the race with a concurrent attach.** The first version of this function re-verified `isImageAssetReferenced` immediately before the row delete, inside the same transaction as that delete, and this document originally described that as closing the window between the initial check and the Blob call. On inspection that's inaccurate: if `editDish`/`createDish` attaches the asset to a `DishVersion` *after* the initial check but *before* the Blob delete call, the recheck correctly leaves the row in place — but the Blob is already gone by then, leaving a saved DishVersion pointing at a deleted Blob object. The 24h age threshold makes this unlikely, not impossible. Fixed by having the transaction take `SELECT ... FOR UPDATE` on the specific `ImageAsset` row *before* the reference recheck and the Blob delete, both of which now run while still holding that lock. Postgres itself requires any concurrent `INSERT`/`UPDATE` that sets a `DishVersion.imageAssetId` to this id to first acquire an implicit `FOR KEY SHARE` lock on the same row (ordinary foreign-key enforcement), which conflicts with `FOR UPDATE` and blocks until this transaction ends — so an attach can no longer land in the gap: either it already committed (the recheck sees it, nothing is touched) or it's forced to wait until this transaction is done, and if this function has by then deleted the row, the previously-blocked attach fails outright with a foreign-key violation instead of silently succeeding against a since-deleted Blob. (`DirectShare.frozenImageAssetIds` has no such FK, but it can't reach a candidate from this sweep anyway — a frozen graph is only ever built by walking an already-attached Dish's content, and every candidate here has zero `DishVersion` references by construction.) Running the Blob call inside a transaction holding a row lock is a deliberate, narrow exception to the usual "external I/O only after commit" discipline, justified because it's the only way to close this specific race with Postgres's own primitives, it locks exactly one row for one call, and this is a low-frequency sequential batch job, not a request path. `ABANDONED_UPLOAD_CLEANUP_TRANSACTION_TIMEOUT_MS` (15s, up from Prisma's 5s default) gives the Blob call headroom within that lock.

**Tests:** `src/lib/images/images.integration.test.ts` — old genuinely-unattached asset is deleted along with its blob; a recently-created unattached asset is retained; an asset attached to a `DishVersion` is retained; an asset referenced by a still-`PENDING` `DirectShare`'s frozen graph is retained; a failed Blob delete retains the DB row rather than discarding it; and (added with the race fix) a concurrent attach fired from inside the mocked Blob delete — i.e. while the sweep's transaction is still open and holding its row lock — is proven to block until that transaction finishes and then fail with a foreign-key violation, rather than silently landing against a since-deleted Blob. `src/app/api/cron/cleanup-orphan-images/route.test.ts` — unconfigured `CRON_SECRET` responds 503, a missing/wrong bearer token responds 401 without running cleanup, and a correctly authorized request runs cleanup and returns its result. Not run this session.

### 2. Metadata/crawler configuration corrected

A code-level audit of production metadata/crawler configuration (not previously covered by this document) found two real `noindex` gaps: `(cook)/layout.tsx` (Cooking Session pages, `/cook/[sessionId]`) and `(share)/layout.tsx` (public token-based share pages, `/s/[token]`) had no `robots` metadata at all, unlike `(app)/layout.tsx`'s existing `{index: false, follow: false}`. The share-page gap was the more significant one: those pages are reachable without authentication, so nothing previously stopped a crawler from indexing them, even though they're only meant to be reachable by someone with the link. Added matching `noindex, nofollow` metadata to both layouts (per standard guidance, `noindex` rather than a `robots.txt` disallow for the share pages specifically, so a crawler can still see the tag and drop any already-indexed URL). Also extended `robots.ts`'s disallow list with authenticated routes that existed but were missing from it: `/meal-plans`, `/grocery-lists`, `/share`, `/settings`, `/cook`. `sitemap.ts` and existing canonical tags were already correct and were left untouched.

**Tests:** new `(cook)/layout.test.ts` and `(share)/layout.test.ts` (asserting the `noindex` metadata), and `robots.test.ts` extended to cover the newly-added disallow entries. Not run this session.
